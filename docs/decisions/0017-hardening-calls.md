## Context

## Decision

### Log and checkpoint correctness (Task 3)
- **`lostCarries`.** A log file's `caregiver.lostCarries` counts the caregiver's carries since the previous file that a restore or a failed life threw away. They are not in `carries` or `to`, and not in the `to` sum. It is an integer >= 1 when present. It is omitted at 0, so a file without loss is byte-identical to before. Over a learner's files, the sum of `carries` and `lostCarries` equals every carry the caregiver made.
  - A restore adds `max(0, carries now − the checkpoint's carries)`, plus the loss earlier restores recorded since the last file. The caregiver state keeps that count as `lost` (optional; absent in older states). The restore's own save holds the restored caregiver with it, so a reload right after a restore keeps the count.
  - A failed life's final file adds the carries lived since its checkpoint to the checkpoint's `lost`.
  - The session counts the carries since the last committed save itself. The count is zeroed only once a save commits, so it is not read back from the caregiver. A save or log write that fails after the caregiver's summary was taken cannot hide carries, and neither can a learner too broken to report.
- **A failed life's final log that cannot be written is reported** on `console.error`, with its reason. Writing it stays best effort, and the life's own error is still the one thrown.
  - Carries lost to a reload or a recoverable (GPU) error are not counted: those resume from the checkpoint without the harness seeing the lost steps. *(Agent's call: left as is; the curve and CU of such steps are not on the record either.)*
- **Tails carry their suite version.** A checkpoint stores `checkups.suiteVersion` (the current `MILESTONE_SUITE_VERSION` when written; a resumed tail keeps its own). Absent, it is suite 1. The tail is checked against that suite's ids, and an unknown version fails to load. A resumed tail of another suite goes into the next log file under its own `milestoneSuiteVersion`, and no new checkup runs until that file is written. One file never mixes two suites.
- **A milestone that throws says why, briefly.** A checkup result with `error: true` may carry `errorReasons`, a map from milestone id to a reason of 1 to 80 printable ASCII characters (`ERROR_REASON_RE`): `${name}: ${message}` with whitespace folded and anything else turned into "?". It is short and bounded so a log stays small and carries no stack or machine detail. It is omitted when nothing threw; older `error: true` results without it still parse. The full error goes to `console.warn` only.
- **A tail needs the learner's evalCU.** A checkpoint whose tail is non-empty must have a learner state with `stats.evalCU` (finite, >= 0). Otherwise it does not load: `"checkups.tail without the learner's evalCU"`. The session checks the same rule before it writes a checkpoint, so it never writes one that would not load. A failed life's final file now carries a non-empty tail always. If evalCU is missing there anyway, writing that file fails explicitly. A tail is no longer dropped silently.
- **`MAX_CHECKUPS_PER_FILE` defers checkups.** While the tail holds 8 results, the next level stays pending (no checkup runs) until a log file takes the tail. A log file with more than 8 is never written: the writer throws.
- **Checkup-score bounds.** A summary row's `checkupScore` is kept only when its level is on the log schedule and its score is an integer from 0 to `MAX_SUITE_SIZE`. `MAX_SUITE_SIZE` is the largest known suite's size (6 now), since summary rows carry no suite version. Anything else reads as null.

### Step speed (Task 2)
- **One GPU round trip fewer a step.** The step reads `lossAfter` with the acting heads in one round, so a step makes 3 serial reads where it made 4. On CPU this is bit-identical to the code before (the golden trajectory, recorded on `5658165`).
- **Measured** (uncapped WebGPU, `GPU_WIDTHS`, Apple metal-3, the same harness, 3 runs each): before (`01d01c5`) 26.75, 26.15, 27.70 steps/s; after (`ba6ce50`) 29.82, 28.74, 30.87 steps/s.
- **Rejected: deferring the actor-critic read to the next step.** It would save another round trip, but it shifts `consecutiveSkips` (which drives the restore after 20 skips), `cu` and `onUpdate` by one step. That is not bit-identical at the harness level, so it is not done.
- **The live speed cap stays 30 steps/s.** A live run can show the gain only up to the cap; the uncapped harness above is the real measure. *(Controller's resolution.)*

### World continuity (Task 5)
- **A resumed learner wakes up in the room it was in.** A checkpoint records `world: { room }`, the room in front at the save (`/^[a-z]{1,16}$/`; absent in older checkpoints and in worlds without `state()`). On a resume (a reload, an adoption, a GPU-loss rerun) and on an in-life restore, the harness brings that room to the front before the next observation. The learner's checkpointed last frame was seen there, so the first resumed transition stays in the same world.
- **Labelled `source: "harness"`.** It goes through `World.bringToFront(kind, "harness")`, a `focus` trace event with `source: "harness"` (the default source stays `"caregiver"`). Neither the learner nor the caregiver chose it. It is not a carry: the caregiver is not called, no `carried` event is emitted and no count in a log file changes. It is not a learner switch: M6 counts only `source: "learner"`.
- **What is not restored:** the cursor and the rooms' own state (scroll, pages, widgets). They are re-created from the seed, as before. A checkpoint without `world`, or with a room the world does not have, resumes where the world starts (skipped, not an error).

### The gate (Task 6)
- **PR files are read with git, not REST.** `loadPrViaGit` makes one gh call (`pulls/N`). It then fetches the head commit that call named, pinned by sha (GitHub serves any reachable commit by its sha; probed): `git --no-lazy-fetch -c fetch.unpackLimit=1 -c transfer.unpackLimit=1 fetch --quiet --no-tags --no-recurse-submodules --filter=blob:limit=1048577 origin +<head sha>:refs/gate/pr-N`, under a byte bound (below). The commit cap therefore binds exactly what is fetched, not a `refs/pull/N/head` that may have moved on. The files are `git --no-lazy-fetch diff --no-ext-diff --no-textconv --no-renames --ignore-submodules=none --raw -z --no-abbrev <merge-base HEAD head> <head sha>`. Each file's size comes from `git cat-file -s` and its bytes from `git cat-file blob`, by the blob id the diff gives at that sha. A PR now costs 1 gh call to load and 1 for its learner's owner (memoised per learner per run), then 2 to merge (`pr ready`, `pr merge --match-head-commit`). At the 16-file cap it was about 34. The gate logs `PR #n: <k> gh calls` per PR.
  - **`--no-lazy-fetch` on every git call that reads objects**, rather than the `GIT_NO_LAZY_FETCH` environment variable. A git older than 2.44 rejects the unknown option and fails loudly; it would silently ignore an unknown variable. Probed: in a partial clone, `git cat-file -s` on a filtered-out 2 MB blob fetched it on demand without the flag, and failed with it. A test shows the same.
  - **At most 64 commits a PR (`MAX_PR_COMMITS`).** This is checked from `pulls/N`'s `commits` before anything is fetched, like the 16-file cap. A tab makes one commit per send, and a send with nothing new makes no commit (`contributor.ts` `commitFiles`). So every commit adds or changes at least one file, and the 16-file cap means about 16 commits; 64 leaves room for re-sends. The real PRs so far (1–22) have at most 4. The fetch brings only the PR's own commits (main's history is already in the checkout), so the cap bounds how many commits' new trees and sub-1 MB blobs it can download. *(Agent's call.)* A shallower fetch (`--depth 1`) would bound the download more tightly, to the head tree's new objects, but it loses the merge base; that would cost a `compare` API call and leave a shallow graft in the checkout, so it was not done.
  - **Every git the gate runs has a 120 s timeout (`GIT_TIMEOUT_MS`), and a PR fetch may write at most 64 MiB (`FETCH_MAX_BYTES`).** *(Agent's calls.)*
    - **How the byte bound is enforced.** `unpackLimit=1` keeps the fetched objects as one pack file, and git runs as `bash -c 'ulimit -f "$1" && shift && exec git "$@"' bash <KiB> <args…>`. The arguments are bash's positional parameters, never shell text (a test passes `$(touch …)` and `;` through it). `bash` rather than `sh` because `ulimit -f` counts 1024-byte units in bash on both Linux and macOS, while `sh` differs (probed: dash counts 512, macOS sh 1024). `prlimit` is not used: it is absent on macOS, so it would be a second path that the tests here never run.
    - **How going over the bound is told.** A pack cut off at the limit is left as a `tmp_pack_*` file exactly the limit's size. The gate removes it and reports the PR as over its bound. Probed: a fetch with a 1 MiB limit failed this way.
    - **Why 64 MiB.** A valid PR is at most 16 files of at most 1 MB plus the trees and commits of at most 64 commits, well under 32 MiB. 64 MiB is twice that.
    - **Going over either bound (time or bytes)** is a `FetchBoundError`. The gate labels the PR `needs-human` at once, during loading, so even a run cut short by the job limit makes progress. It is never fetched again: the gate now skips any open PR that carries `needs-human`, which it did not before; such PRs were re-read and re-labelled every run. A person removes the label to have it decided again. Any other git error (the network, say) still leaves the PR, unlabelled, for the next run.
    - **`gate.yml` has `timeout-minutes: 30`.** With every slow PR labelled the first time it is met, an hourly run cannot be starved by the same PRs again.

  - **One main per run: the checkout (HEAD).** The merge base is taken against HEAD, the earlier logs are read from HEAD's working tree, and the owner from HEAD's history. Validation and the merge base therefore see the same main. If the checkout is older than the PR's base, `HEAD..head` holds main's newer commits as well as the PR's, and its count differs from `pulls/N`'s `commits`. Such a PR is `stale`: it is left for the next run (the gate) or fails the check with "re-run" (the validator), and is never closed, so main's newer files are never taken for the PR's. The same happens if GitHub's count lags. (This replaces fetching main fresh, from the first version of this task, which could disagree with the logs read from the checkout.)
  - **Path taken: git, not the REST fallback.** Probed 2026-10-22: local git 2.54.0; the `ubuntu-latest` (= ubuntu-24.04) runner image documents Git 2.55.0 (`actions/runner-images`, `images/ubuntu/Ubuntu2404-Readme.md`), above the 2.44 that added `--no-lazy-fetch`. On a fresh full clone of `markwhiting/learner`, the fetched `refs/pull/22/head` equalled `pulls/22`'s `head.sha` (`3cc8093…`), and for PRs 1, 5, 8, 11, 12, 15, 18–22 the file list and every file's bytes equalled the REST files list and raw downloads, and `HEAD..head` counted exactly `pulls/N`'s `commits` (none read as stale). No workflow was run to probe the runner itself (not allowed in this task); the runner's git is taken from its published image notes.
  - **The filter limit is 1048577, not 1048576.** `blob:limit=<n>` omits blobs of *at least* n bytes (probed: a blob of exactly 1048576 bytes was left out). The validator allows exactly 1 MiB (`> 1_048_576` is the rule), so the limit is `MAX_BYTES + 1`; the check is the same as before, byte for byte.
  - **Modes and blob ids come from `git diff --raw`**, not a per-file `git ls-tree`: the same head-side mode, with no untrusted path passed back to git as a pathspec.
  - **Every check stays.** More than 16 files is rejected from the PR object before any fetch (and again if the diff itself has more). Only `A` and `M` are allowed; `D`, `T`, `C` and `R` give the same "file status ... is not allowed" text as before (`removed`, `changed`, `copied`, `renamed`). A mode other than `100644`/`100755` (a symlink, a submodule) is "not a regular file". A blob the filter left out cannot be read with `--no-lazy-fetch` and is "file exceeds 1 MB", as is one present but larger. Invalid UTF-8 is rejected.
  - **A head that moved:** if GitHub no longer serves the sha `pulls/N` named (`not our ref`: the branch was force-pushed past it), the PR is `moved`. The gate logs it and leaves the PR for the next run, never closing it. If the old sha is still served (a commit was added on top), it is validated as it is, and the merge pinned to it with `--match-head-commit` is refused; the PR is read again next run. `validate-cli` ends a `moved` run as neutral: it exits 0 with a warning that nothing was validated. Its commit is no longer the PR's head, the run for the new head validates it, and the check is advisory; the gate validates every head itself, pinned to it.
  - **Several PRs for one learner in one run** (checked; no change): every PR is validated against main as of the run's start, and `act` merges at most one per learner per run, the oldest. A later PR that was valid is deferred, not closed, and is validated next run against a main that includes the first (a test with two PRs shows this). One that is invalid even against the older main is closed; a merge of the first could not have made it valid.
  - **Dropped:** the "head repository is unavailable" load error. `refs/pull/N/head` lives in the base repository, so a deleted fork no longer matters for reading the files.
  - **The checkout becomes a partial clone.** The first filtered fetch marks `origin` as a promisor remote in the gate's (and the validator's) throwaway checkout. Nothing there needs the omitted blobs: owner lookups read only commits and trees, and earlier logs are read from the working tree.
- **Who owns a learner: the first merged PR among its commits.** `boundAuthor` walks the commits on main touching `data/runs/<id>/`, oldest first, at most `MAX_OWNER_WALK` = 20. A commit with no merged PR (a direct push) is skipped; the first merged PR's author is the owner. If none of them has one, the learner is unbound, and the first author to get a PR merged claims it. A gh error, a malformed answer or a merged PR without a login still throws, and that learner's PRs are left for the next run. This replaces "the oldest commit must have a merged PR", which left a learner first touched by a direct push stuck forever. *(Agent's call: a dir whose first 20 commits are all direct pushes reads as unbound even if a later commit came through a PR; pushing 20 commits to `main` directly needs write access anyway.)*
- **A shallow checkout stops the run.** `git rev-parse --is-shallow-repository` saying `true` aborts the gate before any PR is decided (and the validator before it validates). It replaces the old inference "logs on main but no owner found means a shallow history", which also caught dirs touched only by direct pushes. `validate.yml` now checks out with `fetch-depth: 0`, as `gate.yml` already did.

### Resolutions the controller made for later tasks (recorded here; those tasks add their own lines)
- **Folder ownership.** A `data/runs/<learnerId>/` folder that only direct pushes have changed is unbound until a PR merges. The author of the first merged PR claims it.
- **Orphaned checkpoints.** A stale or surplus orphan gets a final log file, as a failed life does; its record does not end on a non-final file.
- **The room is restored** with the learner on every restore, the in-life restore after 20 skips included.
- **The gate's fetch path.** The gate probes the `git fetch` path first, with the REST API as the fallback.

## Alternatives considered
- **Counting lost carries in `carries`.** Rejected: `carries` and `to` describe the carries behind the steps on the record. Folding lost ones in would make the counts disagree with the steps and the world the files describe.
- **Labelling a resumed tail with the current suite.** Rejected: its ids would be checked against the wrong suite, and could be refused or silently mean another milestone.
- **Dropping a tail without evalCU from a failed life's final file (the old behaviour).** Rejected: checkup results disappeared from the record without trace (AGENTS.md invariant 7).
- **Running a checkup past 8 and splitting the tail over files.** Rejected: one file would then be written for a reason the log schedule does not have. Deferring is simpler, and the level still runs once.

## Consequences
- Log `schemaVersion` stays 2, `milestoneSuiteVersion` stays 1, and `LEARNER_STATE_VERSION` stays 2. The new fields (`caregiver.lostCarries`, `checkups.suiteVersion`, caregiver state `lost`) are optional and strict when present. Every file under `data/runs/` still parses, and every checkpoint written by `87d115c` code still loads (a non-empty tail there always has a real learner's evalCU).
- A future suite version can ship without stranding checkpoints that hold suite-1 results.
- The parser (`parseLogFile`) is shared by the tab and the gate, so both apply the same `lostCarries` rule.
