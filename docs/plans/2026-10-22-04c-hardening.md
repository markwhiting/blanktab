# Plan 04c — Hardening

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

## In plain terms
Plan 04b got the learner growing up: it now has a caregiver and gets checkups. Its reviews left a list of small things to fix later. This plan fixes them before Plan 05 changes how the learner learns. Nothing here changes what the learner learns or how it is rewarded. The work comes in six parts:
- **The learner can't trip over itself.** Closing it in the middle of a step, or a failed read, won't free memory still in use.
- **Steps are a little faster.** Each step now waits on the GPU three times instead of four. The learning stays exactly the same, and a test proves it bit for bit.
- **The record is complete.** Today a restore or a failed life loses carries without a trace, and a milestone that crashes leaves no reason. Both now go into the logs, and the logs and checkpoints reject impossible values.
- **A reload puts the learner back in the room it was in.** Today it always wakes up in the crib.
- **The gate is cheaper and can't get stuck.** It makes about 3 GitHub API calls per PR instead of about 34. A learner whose folder was edited outside a PR no longer blocks forever. Learners abandoned in a closed tab get a final log.
- **Small page and test fixes:** charts redraw when the window is resized.

**Goal:** fix the deferred robustness, record-keeping and gate problems, and speed up the step, with learning semantics unchanged.

**Architecture:**
- **Learner** (`packages/learner`): every multi-read waits for all its reads to settle before freeing anything; `dispose()` defers its teardown while a step is in flight; one GPU round trip per step is removed by batching reads that were already independent.
- **Harness** (`packages/harness`): the new log and checkpoint fields are additive and optional, strict when present (the `evalCU` precedent). A shared `final.ts` builds the final log for both failed lives and orphans.
- **Gate** (`tools/gate`): it reads PR contents with git from `refs/pull/N/head` (a partial fetch, never executed) instead of two REST calls per file.

**Tech stack:** TypeScript, Vitest, `@blanktab/*` packages, `@napi-rs/canvas` in Node tests, Playwright (e2e, GPU suite, live run), git ≥ 2.44 in the gate.

**Spec:** `docs/specs/2026-10-19-blanktab-v1-design.md` (§7.3, §8, §9.4, §9.5, §10). Also decisions 0011, 0013, 0014, 0015 and 0016, and the new 0017 (Task 3).

## Global Constraints
- **Earlier plans still bind.** Every rule of Plans 04a–04b applies: walls, tensor lifecycle (`packages/tensor/README.md` rules 1–6), cold start, the token rule, and the log and checkpoint invariants.
- **Learning is unchanged.** No change to what the learner learns, its rewards, its settings, milestone thresholds, budgets, the caregiver's policy, the picker or consolidation (those are Plan 05). On CPU, a learner on 04c code gives bit-identical actions, `UpdateInfo`, stats and parameters to one on `87d115c` code (the Task 2 golden test).
- **`LEARNER_STATE_VERSION` stays 2. Log `schemaVersion` stays 2. `milestoneSuiteVersion` stays 1.** New fields are optional, strict when present, and written only when they carry information. Every file under `data/runs/` still parses. Every checkpoint written by `87d115c` code still loads.
- **The new optional fields:**
  - log `caregiver.lostCarries`;
  - log and checkpoint `checkups[].errorReasons`;
  - checkpoint `checkups.suiteVersion`;
  - checkpoint `world`;
  - caregiver state `lost`.
- **Privileged state never reaches the learner** (AGENTS.md invariant 2). The restored room comes back through the world; the learner sees only the frames that follow.
- **No `Math.random`; no `Date` inside the world package.** Any new randomness comes from seeded RNGs.
- **The gate never executes PR content.** It never merges a head it did not validate, and never weakens a check to save an API call (AGENTS.md invariant 7).
- **Agent's calls are labelled.** Every choice this plan makes on the user's behalf is recorded in `docs/decisions/0017-hardening-calls.md` (Task 3 creates it; Tasks 4–7 add their line). It is not yet confirmed by the user.
- **Gates for every task:** run `npm test && npm run typecheck && npm run lint`. Also run `npm run test:gpu` when learner or tensor code changed, and `npm run e2e` when `app/` changed.

## Review Focus
1. **A speed-up that quietly changes learning.** If reads are reordered, any op created in a different order or skipped would change float results. Task 2 records a golden CPU trajectory on the unchanged code, then requires it to be identical afterwards. A test also counts the serial read rounds per step.
2. **A restore, failed life or reload that loses or double-counts a carry, checkup or room.** The required behaviour:
   - lost carries are counted exactly once;
   - checkup levels are never logged twice;
   - the resumed room is not counted as a carry or a learner switch.

   (Tasks 3, 5)
3. **Old data after the change.** Pre-04c logs, a pre-04c checkpoint with a pending checkup tail, and a tail recorded under suite 1 resumed by a later suite version must all load. (Tasks 3, 4, 5)
4. **A gate that saves calls by trusting the wrong bytes.** The gate must:
   - validate exactly the blobs at the head it merges, pinned to that sha;
   - never download blobs over 1 MB;
   - treat a symlink, submodule, rename or delete as an error;
   - when the head moves, wait for the next run instead of closing the PR.

   (Task 6)
5. **`dispose()` while a step, a sleep or a frozen step is in flight.** The step finishes or rejects cleanly, nothing is freed under a pending read, and `liveBuffers` returns to 0. (Task 1)

### Task 2: Step speed — one GPU round trip fewer

**Why (measured live):** run 3 went ~25.5 steps/s against a cap of 30. A step waits on the GPU four times in sequence:
1. `lossBefore`;
2. `lossAfter`;
3. the acting heads and `h_t`;
4. the actor-critic loss and advantage.

`lossAfter` and the acting forward both need only the weights after the prediction update, so they can be read together. The other two waits each gate an update on their value's finiteness, so they stay. **Deferring the actor-critic read into the next step was rejected.** It would shift `onUpdate`, `consecutiveSkips` (which drives the harness's restore after 20 skips) and `cu` by one step, which is not bit-identical at the harness level.   - **`parseSessionRow`.** A `checkupScore` is kept only if `isLogLevel(level)` and `0 ≤ score ≤ MAX_SUITE_SIZE` (both integers). Anything else reads as null.
  - **`lostCarries`.** It is a strict integer ≥ 1 when present. The writer omits it at 0, so files without loss are byte-identical to today's. It is not part of the `to` sum. `takeSummary()` returns `lostCarries: lost` when `lost > 0`, then resets `lost` and `carries`.
  - **Where lost carries come from:**
    - **A restore.** `n = max(0, current.state().carries − (back.caregiver?.carries ?? 0))`. The restored caregiver gets `noteLost(n + (current lost ?? 0) − (back lost ?? 0))`, so the count since the last file is exact.

    - No new checkup runs until that file is written: `checkupAtSleep` returns false while the tail is non-empty and of another version.

    - `fromRecord` checks this after unpacking. Such a checkpoint then takes the existing "checkpoint will not load" path.
    - In `failedLog`, the tail goes into the file whenever it is non-empty. If `evalCU` is missing there anyway, `failedLog` throws `Error("final log: a checkup tail without evalCU")`. That is an explicit error path, no longer a silent drop.
  - **`MAX_CHECKUPS_PER_FILE`, structurally.** `checkupAtSleep` returns false (the level stays pending) while `tail.length >= MAX_CHECKUPS_PER_FILE`. `logFile` throws if `tail.length > MAX_CHECKUPS_PER_FILE`.

### Task 5: A resumed learner wakes up in the room it was in

**Decision (agent's call; recorded in 0017).**
- **What happens.** On resume from a checkpoint (a reload, an adoption, a GPU-loss rerun) and on an in-life restore, the harness brings the checkpoint's room to the front before the first observation.
- **How it is labelled.** It goes through `World.bringToFront(kind, "harness")`, which emits a `focus` trace event with `source: "harness"`. That label is honest: neither the learner nor the caregiver chose it. It is not a carry, because the caregiver is not called and no `carried` event or summary count changes. It is not a learner switch, because M6 counts only `source: "learner"`, and only in checkup variant worlds anyway.
- **Why at all.** The learner's checkpointed last frame was seen in that room. Restoring it keeps the first resumed transition in the same world.
- **What is not restored.** The cursor and the rooms' internal state (scroll, pages, widgets) are not restored. They are re-created from the seed, as today.

**Files:**
- Modify: `packages/world/src/world.ts` (`TraceEvent.source`, `World.bringToFront`)
- Modify: `packages/harness/src/checkpoint.ts` (`Checkpoint.world`, `checkCheckpoint`)
- Modify: `packages/harness/src/session.ts` (`checkpointNow`, resume, the restore path)
- Modify: `docs/decisions/0017-hardening-calls.md` (the decision above)
- Test: `packages/world/test/desktop.test.ts`, `packages/harness/test/checkpoint.test.ts`, `packages/harness/test/session.test.ts`

- Produces:
  ```ts

  // checkpoint.ts
  ```

- **Session:**
  - **Saving.** `checkpointNow` writes `world: { room: world.state().room }` when `world.state` exists.
  - **Resuming.** After the learner is created and before the first `pace()`, call `restoreRoom(cp)`:
    - if `cp.world` is set, `world.rooms` and `world.bringToFront` exist, and `rooms()` includes the room, call `world.bringToFront(room, "harness")`;
    - otherwise do nothing. A room no longer in the world is skipped, not an error.
  - **In-life restore.** The restore path calls `restoreRoom(back)` too.
  - `prevRoom` stays undefined after both, as today.

### Task 6: The gate — about 3 API calls per PR, and no stuck learner

**Findings (checked in the code):**
- **Where the ~34 calls go.** `loadPr` (`tools/gate/github.ts:49-78`) makes:
  - 1 call for `pulls/N`;
  - 1 for `pulls/N/files`;
  - 2 per file in `loadFile`: a contents metadata call, then a raw download.

  At the 16-file cap that is 1 + 1 + 32 = 34. `validate.yml` runs the same `loadPr` on every push to a session PR, so the budget is spent twice.
- **The stuck learner.**
  - `boundAuthor` (`github.ts:90-103`) takes the *oldest* commit touching `data/runs/<id>/` and throws when that commit has no merged PR, i.e. when it was a direct push. The test "throws when the lookup fails: no merged PR …" pins that.
  - `gate.ts` then logs "leaving it for the next run" and skips the PR, every hour, forever.
  - Separately, `gate.ts` skips any learner with logs on main and a null owner (the shallow-checkout guess). A dir touched only outside PRs lands there too.
  - The tab keeps adding to the never-decided PR until it reaches 16 files, then holds its logs forever.

**Decision (agent's call; recorded in 0017).**
- **Reading PR contents.** The gate and the validator read a PR's files with git, not REST:
  - `git fetch --no-tags --filter=blob:limit=1048576 origin +refs/pull/N/head:refs/gate/pr-N` with `GIT_NO_LAZY_FETCH=1`;
  - the fetched head must equal `pulls/N`'s `head.sha`;
  - the file list is `git diff --no-ext-diff --no-textconv --no-renames --name-status -z <merge-base> <head>`;
  - each file's mode comes from `git ls-tree`, its size from `git cat-file -s`, and its bytes from `git cat-file blob`.

  A blob over the filter's limit is never downloaded: with lazy fetch off, reading it fails and is reported as "file exceeds 1 MB". Nothing from the PR is executed: git runs no hooks on fetch, and diff drivers and textconv are off.
- **Who owns a learner.** `boundAuthor` walks the commits touching the dir oldest-first, at most 20. Commits with no PR (direct pushes) are skipped, and the first merged PR's author is the owner.
  - **No such PR among them:** null, meaning unbound; the first author to get a PR merged claims the learner.
  - **The shallow-history guard** becomes an explicit check: `git rev-parse --is-shallow-repository` is `true`, so the run aborts. It replaces the inference from "logs but no owner".

**Files:**
- Modify: `tools/gate/github.ts` (`loadPr` → `loadPrViaGit`; `boundAuthor`; a call counter on `gh`)

### Task 7: Orphans get a final log
